# 通用游戏世界模拟接入指导书

版本 1.1 | 2026-10-18 | 面向原本没有智能交互的单机或在线游戏

## 0. 这份指导书解决什么问题

把大模型接到游戏里，最容易做成的是“聊天窗口”；最难做成的是一个会随时间、规则、资源、关系和历史变化而自洽的世界。本指导书给出一套可迁移的工程方法：先把原游戏的事实、规则、时间和可执行接口整理成契约，再让模型承担理解、提议和叙事，把所有状态提交交给确定性引擎，最后通过回执、记忆、校验和测试把结果闭合。

适用对象包括 RPG、经营、模拟、策略、沙盒、互动叙事，以及通过 Mod、插件或外部服务接入模型的既有游戏。指导书不要求原游戏重写为新引擎；优先采用适配器、投影层和能力目录，把原有逻辑保留下来。

本书中的“事实”指已经被游戏或适配器确认的状态；“提议”指模型希望发生但尚未生效的内容；“投影”指给玩家看的文本、图像、声音或 UI。三者必须分开保存和校验。

## 0.1 最短判断标准

一个接入方案至少要同时满足以下九点：

- 模型不能直接写核心数值、库存、生命、任务完成状态或存档。
- 每个模型输出都必须落到结构化协议，未知字段丢弃，缺失字段有默认值。
- 任何写入都要经过规则检查、前置条件检查、权限检查和结果验证。
- 生成内容与手工内容走同一套注册和消费流程。
- 交易、移动、战斗、任务、关系变化等行为必须有幂等键，重复请求不会重复扣款或重复生成。
- 世界必须有修订号或等价的并发快照，过期回复不能污染当前状态。
- 网络模型失败、超时、返回无效数据时，游戏仍能继续运行。
- 角色的人格、记忆、关系和情绪要随时间演化，不把一张静态人设卡当作完整人物。
- 每次重要变化都能回答：谁提出、依据是什么、何时生效、由谁执行、结果是否验证、失败后怎么恢复。

其中“角色状态随时间演化”是通用设计目标和起始原则，公开研究分别验证了记忆、角色表现或社交互动的局部机制，尚未证明大规模长时段下人格、关系、情绪和事实都能稳定演化。

## 0.2 阅读方式与证据等级

本书把建议分为三种用途类别。资料中已经在工程或实验中落地的做法，标为“已验证模式”；从这些模式抽象出的跨游戏规则，标为“通用要求”；需要根据题材、性能和商业目标调整的数值，标为“起始参数”。用途类别描述建议应该怎样使用，不能替代外部证据强度。

研究证据采用三条轴记录，见第 21 章：证据类型（E0 工程不变量、E1 基准或多项研究、E2 单项研究、公开原型或架构框架、E3 项目内观察、H 启发式）、直接性（D1 直接验证原生状态，D2 在工具或代理环境中间接验证，D3 理论或类比）和外部效度（X1 已有跨题材复现，X2 只在有限环境迁移，X3 尚未验证）。例如，“引擎拥有最终裁判权”是 E0/D1/X2 的安全设计原则；Generative Agents 的记忆、反思和计划是 E2/D2/X2 的研究原型；本书的 PCC 阈值属于 E3 或 H，必须由接入项目重新标定。

### 0.3 规范性语言与证据标签

本书使用以下规范性语言：

- MUST：不满足时会破坏事实正确性、权限边界、存档可靠性或恢复能力，必须实现。
- SHOULD：强烈建议实现；如果题材、性能或平台限制导致无法实现，必须记录替代方案和风险。
- MAY：可选能力，只有在测试、成本和玩家体验允许时启用。

每条关键要求都应同时回答“要求是什么”“证据来自哪里”“在哪个环境重新验证”。研究论文可以支持设计方向，不能自动证明商业游戏中的状态正确、长期稳定或玩家接受。生产系统的最终验收仍以原生回执、固定种子回放、长程压力测试和玩家研究为准。

## 1. 总体原则

### 1.1 引擎是唯一裁判

模型可以理解玩家意图、生成行动提案、撰写叙事、提出新内容，但不拥有最终状态写入权。游戏引擎、原生 API 或受控适配器负责判断状态是否允许变化，并返回可审计结果。

推荐把每轮交互拆成三段：

1. 感知与理解：从玩家输入和当前可见世界中提取意图。
2. 提议与校验：生成候选动作或内容，经规则、风险和能力边界检查。
3. 提交与投影：引擎提交状态，适配器确认原生结果，模型或模板生成玩家可见表达。

### 1.2 模型只提议，不直接生效

模型输出的动作、物品、关系、事件和世界修改，都先进入 Proposed 状态。只有注册成功、前置条件满足并收到执行回执，才转为 Active 或 Completed。无法确认的内容保持 Pending、Rejected 或 Deferred，不用叙事文本假装已经发生。

### 1.3 手工内容与生成内容同构

手工设计的任务、物品、状态、事件和模型生成的同类内容，应共享同一数据结构、校验器、效果注册表和 UI 投影器。否则会出现“策划内容可回放、模型内容不可回放”的双轨系统。

### 1.4 覆盖规则，不宣称违反规则

世界出现局部例外时，记录一个有范围、有条件、有时效的覆盖或修正器，而不是让模型宣称原规则失效。覆盖必须有来源、成本、边界、衰减函数和撤销方式。

### 1.5 先模拟，再提交

低风险表达可以走快速路径；涉及核心资源、死亡、永久关系、关键人物、规则变更或跨角色行动的提案，先做后果估计和必要的多分支推演，再交给确定性校验器提交。

### 1.6 渐进式降低幻觉影响

不要把“模型永不出错”当作前提。用多道闸门把错误限制在局部：

- 结构闸门：JSON、类型、长度、枚举。
- 事实闸门：人物、物品、位置、时间和任务是否存在。
- 规则闸门：数值范围、资源成本、前置条件和权限。
- 因果闸门：行动顺序、延迟后果、依赖关系。
- 叙事闸门：输出是否把未生效提议说成既成事实。
- 回退闸门：失败时使用本地规则、模板或自然拒绝。

### 1.7 涌现是信号，不是自动真相

规则组合可能产生设计者未预先写出的结果。系统应记录实际结果与预期结果的偏差，区分有益、危险、循环和中性涌现。只有确定性引擎确认的结果才能改变状态；模型只负责解释、归纳和生成后续候选。

### 1.8 权限与可见性先于提示词

模型看到的不是完整数据库，而是按角色、位置、知识、时间和信息来源过滤后的视图。玩家、NPC、GM、后台审核器可以拥有不同的知识集。私密记忆不得因为“上下文很长”而泄漏给不该知道的人。

### 1.9 叙事不能修复事实

叙事可以解释未知、补足气氛、描述已经发生的结果，但不能把已经确认的死亡改写成没死，不能凭空创造不存在的物品，也不能用“其实是替身”消除已记录的因果。逆向解释只适用于引擎标记为“待解释”且不改变历史事实的异常。

### 1.10 核心主张与证据边界

本书的核心主张分成三类，实施时不要混用：

| 主张 | 证据标签 | 可接受的验证 |
| --- | --- | --- |
| 原生状态拥有最终裁判权，模型只能提交提案 | E0/D1/X2 | 原生回执、写入拦截测试、越权红队、存档回放 |
| 记忆、反思、计划、工具接地和技能库能改善代理行为 | E1/E2/D2/X2 | 论文基线、公开基准、固定种子回放、长程对照实验 |
| 某个阈值、提示模板或人格评分在所有题材都有效 | H 或 E3/D2/D3/X3 | 只能作为项目起始参数，必须按题材重新标定 |

研究原型常常拥有更简单的状态空间、更少的角色和更短的实验窗口。它们能够说明一个机制值得试验，不能替代对原生引擎、并发、存档、成本和玩家体验的验收。指导书中所有“研究表明”的句子都应在附录 A 找到对应的 claim_id 和限制条件。

## 2. 接入前的游戏考古

不要从“选哪个模型”开始。第一阶段的目标是把原游戏变成一份可读取、可调用、可回放的事实清单。

### 2.1 盘点七类系统

| 系统 | 必须回答的问题 | 输出物 |
| --- | --- | --- |
| 实体 | 人物、物品、地点、组织、任务、状态各自的稳定标识是什么 | 实体目录与别名表 |
| 规则 | 哪些值由公式、脚本、随机数或原生系统决定 | 规则清单与参数范围 |
| 时间 | 时间以帧、秒、回合、天还是事件推进，能否快进 | 时间模型与触发器 |
| 事件 | 事件如何创建、排队、取消、完成、失败、重放 | 事件生命周期 |
| 持久化 | 存档写哪些字段，版本如何迁移，崩溃如何恢复 | 存档契约 |
| 交互 | 玩家输入从哪里进入，原生确认点在哪里 | 输入/输出边界 |
| 观察 | 如何验证一个动作真的在游戏中生效 | 读取点、回执和探针 |

### 2.2 把事实与叙事分开建模

建议至少建立以下记录：

~~~
Entity:
  stable_key
  display_name
  native_identifier
  type
  aliases
  visibility_scope

Fact:
  fact_key
  subject_key
  predicate
  value
  source
  confidence
  observed_at
  immutable

Event:
  event_key
  kind
  start_time
  deadline
  prerequisites
  effects
  visibility
  status

NarrativeProjection:
  source_event
  audience
  tone
  text
  generated_at
~~~

事实记录可以被规则和查询使用；叙事投影必须引用事实或已批准提案。不要把一段自然语言当作唯一状态源。

### 2.3 查清原生写入点

对每个计划接入的行为，记录三个位置：

1. 提案入口：模型或玩家可以表达什么。
2. 执行入口：哪个原生方法真正改变状态。
3. 验证入口：执行后如何读取结果。

如果只有入口没有验证入口，先把能力定义为“提议”或“等待原生确认”，不要把模型回复当作成功。

### 2.4 先画边界图，再写代码

最低限度要画出以下链路：

~~~
玩家输入
  -> 当前感知视图
  -> 意图分类
  -> 结构化提议
  -> 预测/风险
  -> 确定性规则校验
  -> 能力适配器
  -> 原生执行
  -> 回执与修订号
  -> 记忆/因果/事件
  -> 叙事与 UI 投影
~~~

凡是绕过这条链路直接写数据库、直接改原生对象或直接把模型文字显示给玩家的代码，都应标为高风险。

### 2.5 研究证据映射与可研究性包

接入考古阶段可以借用公开研究的观察维度，但要把它们翻译成原生游戏的可测对象：

| 考古对象 | 研究参照 | 接入时必须落地的产物 |
| --- | --- | --- |
| 记忆、计划和角色经历 | Generative Agents、CoALA、MemoryBank | 事件引用、记忆权限、摘要版本、检索结果和遗忘策略 |
| 可执行动作与前置条件 | SayCan、ReAct、Voyager | 能力目录、动作 schema、前置条件、执行回执和失败分类 |
| 视觉或黑盒控制 | SIMA、Cradle | 观测快照、动作录制、画面与内部状态对齐、人工接管边界 |
| 多主体社交和叙事涌现 | SOTOPIA、MACHIAVELLI、Player-Driven Emergence | 角色视角、社会目标、关系变化、玩家研究和安全审计 |

这些研究不能证明商业游戏的全状态迁移一定正确。每个接入项目都要生成一份“可研究性包”：游戏构建号、适配器版本、schema/rules/prompt/model 版本、固定 seed、初始快照 hash、输入序列、所有提案与校验轨迹、原生回执、随机数流、指标脚本和失败样本。没有这份包，后续无法区分模型变化、规则变化和适配器变化造成的回归。

## 3. 通用接入架构

### 3.1 参考架构：六个平面与一个提交闸门

通用接入架构应按“谁拥有状态、谁可以写入、失败如何恢复”划分，而不是只按代码模块名称划分。模型服务是可替换组件，提交闸门和原生引擎是不可绕过的边界。

~~~
玩家输入 / 原生事件
        -> 观测与可见性过滤
        -> 角色认知平面
        -> 模型服务平面
        -> 结构化提案
        -> 统一提交闸门
             -> 权威平面执行
             -> 回执与修订号
        -> 世界状态平面
        -> 事件、记忆、因果与指标
        -> 投影平面

证据控制平面贯穿所有读写、权限、失败和回放路径
~~~

| 平面 | 主要职责 | 状态所有者 | 允许写入 |
| --- | --- | --- | --- |
| 权威平面 | 原生事实、硬规则、原生模拟、原生存档和最终执行 | 游戏引擎或服务端 | 只通过原生写入点 |
| 世界状态平面 | 规范化快照、扩展事实、世界时间、事件、因果图和派生状态 | 接入层状态服务 | 受控、可迁移、可对账 |
| 角色认知平面 | 感知、身份、记忆检索、评价、计划、情绪和行动提议 | 角色运行时 | 只能写提案、记忆候选和复盘 |
| 模型服务平面 | 模型路由、提示、结构化输出、重试、超时和成本控制 | 模型网关 | 不拥有游戏状态 |
| 证据控制平面 | 可见性、权限、schema、事实、规则、风险、账本、回放和指标 | 确定性守卫与审计服务 | 可阻断、延期、标记和记录 |
| 投影平面 | 对话、日志、动画、音频、UI 和多模态表达 | 客户端或展示服务 | 只能读取已确认结果 |

四条所有权规则必须写进接口契约：原生引擎拥有原生事实和最终写入权；世界状态平面拥有扩展事实和派生记录；角色运行时拥有短期认知状态和提案；模型服务不拥有任何事实。证据控制平面拥有审计轨迹，但不能凭空制造结果。

### 3.2 两个主循环

同步提交环负责玩家当前动作和必须立即确认的变化：

~~~
observe -> build_view -> propose -> validate -> execute_native
        -> read_receipt -> reconcile -> project
~~~

异步世界环负责时间推进和没有玩家即时输入的变化：

~~~
advance_time -> schedule_events -> update_world_state
             -> wake_relevant_agents -> propose -> submit_gate
~~~

同步提交环决定“这次变化是否真的发生”；异步世界环决定“在没有玩家操作时，哪些已授权事件继续推进”。两条环共享同一套规则、能力、修订号和账本，不能为异步角色另设一套可以绕过校验的写入口。

### 3.3 三种上下文

- 状态上下文：当前数值、实体、位置、资源、事件、规则修正和版本号。
- 知识上下文：当前角色按可见性可以知道的事实、记忆和关系。
- 任务上下文：本轮输入、目标、候选能力、预测摘要、风险级别和输出格式。

这三种上下文分别构建、分别截断、分别记录来源。不要把整个存档序列化后直接塞进提示词。角色认知平面只接收与当前角色和场景相符的视图，证据控制平面保存视图 hash，便于检查信息泄漏和重放差异。

### 3.4 三条数据流

1. 读流：原生状态 -> 规范化快照 -> 可见性过滤 -> 模型上下文。
2. 写流：模型提议 -> 能力校验 -> 原生执行 -> 结果回执 -> 扩展状态。
3. 旁路流：事件日志 -> 记忆摘要、因果图、指标、回放和红队样本。

读流失败时应降级为最小上下文；写流失败时不能静默成功；旁路流失败不能阻断核心玩法，但必须记录。所有写流都通过提交闸门，旁路流不得反向修改原生事实。

### 3.5 证据卡：模块化比单一提示更重要

CoALA 将语言代理组织为模块化记忆、结构化行动空间和决策过程；ReAct 说明交替的观察、推理和行动有助于处理外部反馈；SayCan 进一步要求高层语言计划落到环境可执行的能力上。这些研究共同支持本章的分层架构，但研究环境通常没有商业游戏的完整存档、并发和权限边界。工程验收必须回到快照一致性、能力回执、状态修订号和回放结果（对应 C-002、C-006）。

## 4. 规则体系与状态模型

### 4.1 四级规则

| 级别 | 说明 | 典型处理 |
| --- | --- | --- |
| 元规则 | 因果律、资源守恒、规则可演化但需付出成本 | 违反即拒绝 |
| 硬规则 | 物理、伤害、库存、数值上限、权限 | 布尔校验，不能由模型协商 |
| 软规则 | 社会规范、AI 行为偏好、概率性后果 | 概率评估，允许受控例外 |
| 局部覆盖 | 地区、装备、天气、事件、状态带来的修正 | 有范围、条件、期限和衰减 |

未定义行为不能默认由模型自由决定。可选策略是：请求澄清、暂时冻结、使用安全默认值，或进入待裁决队列。

### 4.2 规则解析器

~~~
resolve(parameter, position, time, context):
  1. 读取当前有效的局部覆盖
  2. 应用覆盖的时空衰减
  3. 读取软规则的上下文修正
  4. 返回全局默认值与修正后的结果
  5. 附带来源、版本和有效期
~~~

规则解析结果必须可解释。不要只返回一个数字，还要能回答“这个数字来自哪条规则、哪个覆盖、哪项上下文”。

### 4.3 世界状态最小字段

~~~
world_id
schema_version
rules_version
state_revision
game_time
seed
entities
facts
active_modifiers
active_events
pending_intents
relationships
memories
causal_edges
last_resolution_hash
~~~

所有外部动作都带上 world_id、state_revision、actor、capability_key、arguments 和 request_id。修订号不一致时，保留文字但剥离过期动作，或要求重新生成。

### 4.4 存档与迁移

存档必须有 schema_version 和 migrate(old -> new)。新增字段有默认值，删除字段要有兼容读取，迁移失败不能覆盖原存档。写入使用临时文件、备份和原子替换；关键变更保留事件日志或可恢复快照。

## 5. 能力目录与原生适配器

### 5.1 能力不是函数名，而是契约

每项能力至少描述：

~~~
capability_key
version
title
description
supported_scenes
risk_level
permissions
preconditions
safe_timings
effects
idempotency_fields
verification
failure_description
~~~

能力目录应同时供模型、校验器、GM/审核器和 UI 使用。模型只能从目录中选择，不能创造新接口。

### 5.2 风险分级

| 级别 | 例子 | 默认流程 |
| --- | --- | --- |
| R0 只读 | 查询人物、查看规则、读取库存 | 可直接返回 |
| R1 扩展状态 | 记录记忆、建立任务、提出关系变化 | 校验后写扩展存储 |
| R2 可恢复原生 | 安排回访、调整临时报价、打开可取消流程 | 检查快照、幂等与回执 |
| R3 敏感原生 | 扣款、交换、删除、死亡、永久关系、规则修改 | 多分支风险检查，必要时人工确认 |

### 5.3 前置条件与结果验证

~~~
propose -> check_preconditions -> approve
        -> execute_native -> read_receipt
        -> verify_postconditions
        -> complete | deferred | rejected | conflict
~~~

没有 postconditions 的能力不应被标记为“已完成”。例如“答应找货”只能创建委托；找到、入库、交付分别是后续状态。

### 5.4 幂等与恢复

幂等键建议由 world_id、session_id、turn_id、能力键和规范化参数组成。账本至少记录 Proposed、Executing、Completed、Deferred、Rejected、Conflict、Compensated、Expired。进程退出时，Executing 不自动重放；先标记为待重新核对，再由适配器读取原生状态。

### 5.5 证据卡：能力接地不等于状态正确

SayCan 的核心启发是让语言模型选择环境中已有、可执行且符合当前状态的技能；Voyager 将执行代码、环境错误和自我验证组成技能库；SIMA 与 Cradle 展示了通过视觉和键鼠接口控制多个虚拟环境的路线。它们支持“动作必须接地到能力”的设计，却没有证明黑盒控制能够可靠读取商业游戏的全部内部事实。优先使用原生适配器；只能使用视觉或键鼠控制时，必须增加人工接管、画面与状态对账以及失败后冻结写入（对应 C-002、C-008）。

## 6. 模型协议与提示上下文

### 6.1 双模型职责

推荐至少区分人物/叙事模型与监督模型：

- 人物模型：在可见上下文中表达角色，提取本轮明确意图和提案。
- 监督模型：不扮演人物，只复核目标、能力路径、权限、原生前置条件和提案一致性。

监督模型也不能直接写状态；它只能返回第二份提案或拒绝理由，最终由确定性引擎执行。

### 6.2 七区上下文

| 区域 | 内容 | 说明 |
| --- | --- | --- |
| Identity | 角色定位、硬边界、输出职责 | 稳定，低频更新 |
| Scene | 当前场景行为准则 | 按场景加载 |
| Classification | 输入分类和处理策略 | 明确当前要做什么 |
| State Snapshot | 世界、角色、资源、时间、修订号 | 只放必要字段 |
| Prediction | 预测摘要、风险、可选分支 | 不把隐藏链式思考原样暴露 |
| Retrieved Memory | 相关记忆、事实和因果 | 带来源、时间、可见性 |
| Recent Dialogue | 最近若干轮对话 | 超出预算后压缩 |

### 6.3 稀疏结构化输出

模型只返回本轮发生的字段，未发生的行为不要填空对象。解析器补默认值，并拒绝未知字段或把未知字段放入诊断区。

~~~
{
  "reply": "玩家可见的角色回复",
  "mode": "continue",
  "intent": {
    "kind": "trade|visit|quest|query|none",
    "confidence": 0.0
  },
  "proposals": [
    {
      "capability_key": "visit.request.self",
      "arguments": {},
      "reason": "人物明确答应下次回访"
    }
  ],
  "signals": {
    "warmth": 0,
    "trust": 0,
    "offense": 0
  },
  "memory_candidates": [],
  "warnings": []
}
~~~

### 6.4 提示词最重要的四句话

1. 原生状态是事实来源；扩展摘要不能覆盖原生事实。
2. 你只能使用上下文明确提供的知识。
3. 你只能提出目录中存在的能力。
4. 未收到执行回执时，不要说动作已经生效。

## 7. 预测、规划与风险

### 7.1 系统一与系统二

快速路径用于低风险的查询、普通对话和局部叙事；慢速路径用于多步计划、关键资源、规则修改、永久影响和高不确定性行为。慢速路径可以模拟多个候选，但所有候选都必须再经过硬规则校验。

### 7.2 预测结果格式

~~~
prediction:
  horizon
  branches:
    - proposed_action
      projected_changes
      confidence
      risk_score
      violated_rules
      delayed_consequences
  overall_risk
  assumptions
~~~

预测不是事实，不得写入世界事实库；它应作为提案上下文和后续训练/调参样本保存。

### 7.3 风险起始阈值

| 风险 | 建议路径 |
| --- | --- |
| 0.00 - 0.19 | 快速结构与规则检查 |
| 0.20 - 0.59 | 标准校验，记录关注项 |
| 0.60 - 0.89 | 多分支推演、深度校验、必要时延迟 |
| 0.90 - 1.00 | 默认拒绝执行或转为自然阻碍，除非已有明确授权 |

这些是起始参数，应通过回放和玩家体验调整。不要让模型单独决定阈值含义。

### 7.4 延迟后果

行为记录 immediate_effect 与 delayed_effect。延迟项至少包含触发时间、概率、条件、来源、可见范围、取消/补偿策略。时间推进时按条件重新检查，不在创建时把所有后果一次性写死。

### 7.5 世界模型边界与预测校准

World Models、DreamerV3、Genie 和 GameNGen 代表另一条路线：模型学习像素或潜在状态的变化，并在模型内部想象未来。它们适合做预测、训练和测试，但预测结果是 non-authoritative，不能直接写入事实库、库存、碰撞、任务完成或存档。预测服务必须返回模型版本、输入快照、分支条件、置信度和有效期（对应 C-005、C-012）。

至少记录三类校准指标：离散事件概率使用 Brier score 或 ECE；分支预测记录固定窗口内的命中率与覆盖率；延迟后果记录 precision、recall 和提前量。预测偏差只能触发风险升级、提示或重新规划，不能绕过原生校验器。视觉生成模型可以作为演练环境或投影层实验，但不能替代原生规则和回执。

## 8. 记忆、事实与因果

### 8.1 四类记忆

- 工作记忆：本轮上下文和近期对话。
- 情景记忆：某次经历、地点、参与者、结果和情绪。
- 语义记忆：从多次经历归纳的稳定事实或规律。
- 程序记忆：角色通常如何处理某类情况的行为习惯。

每条记忆都带角色范围、可见性、来源、创建时间、重要度、正负情绪和过期/衰减策略。

### 8.2 分层摘要

建议按日、周、月或题材相当的时间窗生成摘要；摘要只引用已记录事件，不凭模型补造事实。保留原始事件的引用键，便于回放和纠错。

### 8.3 检索

先按权限、角色、场景和时间过滤，再用关键词、向量或混合方法排序。检索结果带 relevance、source、confidence 和 visibility。检索不到时保持空结果，不用相似文本填补。

### 8.4 世界事实库

世界事实应区分 immutable、manual、native、observed、ai_proposed 等来源。与不可变事实冲突直接拒绝；与高置信度事实冲突进入复核；低置信度新事实可以标为待确认。主工程中的世界事实刷新、检索增强和边界校验可作为通用实现参考。

### 8.5 因果图

每次状态变化都记录 cause -> effect。关系边带时间、来源、置信度、可见性和是否为涌现节点。因果图不是装饰：它用于生成延迟后果、解释任务为何出现、检索与当前事件有关的历史，以及回放同一局面。

### 8.6 证据与未决问题

Generative Agents、MemoryBank 和 CoALA 支持“经历记录、摘要/反思、按情境检索”的组合；它们主要在小规模文本或沙盒环境中验证可信行为，不能证明数百轮以上的事实、记忆和因果永不漂移。SOTOPIA 与相关社交研究也显示，模型在复杂社会常识和策略沟通上仍可能低于人类。

因此，记忆系统必须同时接受事实精度、来源覆盖率、过期记忆误用率、关系漂移和任务连续性测试。检索不到时返回空结果，记忆冲突时保留冲突证据；模型的摘要和反思不得覆盖原始事件（对应 C-003）。

## 9. 动态角色一致性

### 9.1 身份与状态分离

静态人设卡只能说明“这个角色是谁”，不能说明“此刻为何这样反应”。建议把角色拆成三层：

| 层 | 含义 | 更新速度 |
| --- | --- | --- |
| L Identity | 天生/习得特质、价值底线、表达偏好、知识边界 | 原则上不变 |
| M Meaning/Strain | 目的感、压力、信任债务、长期疲劳、关系解释 | 缓慢累积 |
| S Affect | 当前情绪价度、强度、即时警觉和冲动 | 每轮可变 |

### 9.2 状态转移

~~~
next_state = Transition(previous_state, event, identity, appraisal)
S_next = clip(S + delta_S, 0, 10)
M_next = clip(M + delta_M, 0, 10)
~~~

事件影响不应只由事件名称决定；同一件事对不同身份产生不同变化。状态变化要有原因、幅度上限和衰减。

### 9.3 表达约束

角色不必每句话都展示全部特质；“未体现”不能误判为“违反”。但一旦出现与身份冲突的表达，应拦截或重写。内部《动态人格一致性》研究中的 PCC 可作为起始评估：

~~~
L-score = 0.4 * min(attribute_scores) + 0.6 * average(attribute_scores)
PCC = min(L-score, (S-score + M-score) / 2)
~~~

起始策略：PCC 小于 0.60 时触发纠偏；PCC 达到 0.85 的高质量案例才进入案例库；纠偏后达到 0.60 才接受。案例检索先按场景过滤，再以 0.6 的语义相似度与 0.4 的状态接近度混合排序。上述数字来自内部研究的起始参数，不是公开论文共同提出的阈值，也不是跨游戏定律。

### 9.4 纠偏闭环

~~~
生成 -> PCC 分解评分 -> 低于阈值则纠偏
     -> 二次评估 -> 可接受则返回
     -> 高质量样本进入角色案例库
~~~

纠偏时优先保留当前情绪，再修复身份冲突；不要把所有角色都修成“平静、礼貌、正确”的同一种声音。

### 9.5 PCC、PCR、PDS 的证据与适用边界

公开人格研究能够支持“人格会在交互中出现一致性差异”和“身份、经历、情绪需要分别建模”这两个方向，但不能证明本书的 L/M/S、PCC、PCR、PDS 公式对所有题材都成立。尤其是 0.60、0.85、0.6 等阈值只能作为本项目起始参数；必须按语言、题材、角色数量、对话长度和评审标准重新标定。

自动评分与人工判断冲突时，保留两份结果和冲突原因。评估集至少包含身份事实、价值取向、关系状态、压力变化、拒绝越权和跨轮记忆六类场景，并报告每类样本数、置信区间和失败例子（对应 C-004）。

## 10. 多智能体、感知与时间

### 10.1 多智能体协调

每个角色只看到自己的感知视图。多个角色的提案进入统一队列，按优先级、时间戳、资源冲突和能力风险排序。冲突必须有确定性决策，不要让多个模型各自声称已经占用同一资源。

### 10.2 多尺度时间

物理、行动、事件、叙事和纪元可以使用不同粒度。无事件区间可以压缩，有玩家相关或关键节点事件时恢复正常推进。时间压缩的结果必须仍然生成可解释的摘要和延迟后果。

### 10.3 世界不会无限等待

关键任务应定义参与、错过、越阶参与、延期和失败状态。时间推进时，事件调度器综合截止时间、因果连接、关系压力、最近互动和记忆衰减，生成有限的重点提示，不把全部任务强行塞给模型。

### 10.4 证据与未决问题

SOTOPIA、Social NPCs Skyrim、Collaborative Quest 和叙事涌现研究说明，角色视角、社会目标、关系变化和玩家互动可以产生可观察的群体行为；这些结果大多来自小规模、短时段或文本/特定游戏实验。它们不能直接证明数百名角色长期运行时仍然公平、稳定、可回放。

多主体接入要单独测试信息泄漏、资源争用、优先级饥饿、循环事件、关系极化和玩家自主感。每个角色的提案都要带感知视图版本，统一调度器才有权决定资源占用和事件提交（对应 C-007）。

## 11. 一轮交互的完整流程

推荐把以下步骤作为统一流水线，所有场景共用：

1. 捕获输入、场景、角色、会话和世界修订号。
2. 读取原生事实，构建最小可见状态。
3. 读取角色记忆、关系、任务、世界事实和近期对话。
4. 分类输入：查询、对话、行动、交易、规则修改或越界请求。
5. 选择提示模板与输出 schema。
6. 调用人物/叙事模型生成结构化结果。
7. 解析 JSON，清理未知字段，执行类型与长度检查。
8. 做人格、事实、叙事契约和权限检查。
9. 对高风险提案做预测、多分支和监督复核。
10. 通过能力目录执行原生适配器，取得回执。
11. 写入扩展状态、事件、记忆、因果边和指标，推进修订号。
12. 根据已确认结果生成叙事和 UI 投影。
13. 保存快照、账本和回放样本；失败则调用回退策略。

任何一步失败都要返回明确状态：Rejected、Deferred、Conflict、Fallback 或 Partial，而不是一个看起来正常的字符串。

### 11.1 可重放执行契约

每次交互至少保存以下字段，并保证字段之间可以通过 request_id 和 snapshot_revision 关联：

~~~
trace_id
input_hash
world_id
snapshot_revision
proposal
check_results
adapter_version
execution_request
native_receipt
postcondition_result
projection
seed
failure_or_recovery
~~~

ReAct 或 Reflexion 这类方法可以用于生成提案、收集环境反馈和形成复盘，但推理轨迹本身不是授权凭证，也不能替代原生回执。离线重放时固定模型 profile、规则版本、适配器版本和随机数流；线上模型只允许提交同一 schema 的候选结果。

## 12. 校验、回退与安全

### 12.1 校验矩阵

| 校验 | 检查内容 | 失败动作 |
| --- | --- | --- |
| Schema | JSON、类型、枚举、长度、必填字段 | 重新生成或本地模板 |
| Fact | 实体、身份、位置、物品、历史事实 | 拒绝并给自然回应 |
| Rule | 硬规则、软规则、资源、上限、权限 | 拒绝或修正参数 |
| Capability | 能力存在、场景支持、前置条件、时机 | 延期、澄清或拒绝 |
| Consistency | 人格、关系、时间线、因果和任务连续性 | 纠偏或标记复核 |
| Prediction | 预计风险、分支和长期后果 | 升级审核或阻断 |
| Output | 已生效与未生效的措辞、UI 字段和多模态一致性 | 重写投影 |

### 12.2 错误分级

- L1：硬规则、权限、事实身份冲突，直接阻断。
- L2：schema 或能力参数错误，最多有限次数重试。
- L3：平衡、语气或低置信度事实问题，修正并记录。
- L4：预测偏差或叙事轻微不自然，允许执行但进入评估集。

### 12.3 回退层级

1. 同一模型重试，缩短上下文并保留请求摘要。
2. 切换备用模型或协议。
3. 本地规则和模板生成安全回复。
4. 保留已确认状态，延迟未确认动作。
5. 记录错误和可重放输入，继续游戏主循环。

### 12.4 安全边界

模型请求必须有超时、取消、最大输出长度、网络开关和密钥隔离。GM 或世界修改接口必须使用白名单字段、幅度和期限；允许网络与否要成为配置项。多用户游戏还要加入玩家身份、租户隔离、服务端权威和速率限制。

### 12.5 威胁模型与证据来源

| 威胁 | 预防 | 检测与回退 | 必留审计字段 |
| --- | --- | --- | --- |
| 提示注入或恶意上下文 | 分离数据与指令，能力白名单 | schema/权限校验，拒绝提案 | 原始输入 hash、过滤结果 |
| 工具越权或参数篡改 | 最小权限、参数范围、服务端校验 | 原生拒绝，冻结动作 | actor、capability、参数摘要 |
| 跨角色信息泄漏 | 角色视图和记忆 visibility | 脱敏、隔离、红队回放 | source、audience、visibility |
| 重放攻击或重复执行 | request_id、幂等键、过期修订号 | 查询账本后补回执 | request_id、revision、ledger_state |
| 并发竞态与资源争用 | 版本检查、统一调度、原子提交 | Conflict、重新规划 | lock/version、冲突双方 |
| 模型或供应链变化 | 固定 profile、版本锁定、备用模型 | 回退到本地规则 | model_profile、provider、prompt_hash |

OWASP LLM Top 10、NIST AI RMF 和 ISO/IEC 23894 可以作为工程安全参考，但它们与游戏行为论文属于不同证据类别；安全标准能帮助建立控制项，不能代替目标游戏的状态、存档和玩家体验测试。

## 13. 测试与评估

### 13.1 测试分层

| 层级 | 目标 | 最小样本 |
| --- | --- | --- |
| 单元测试 | 规则、解析、迁移、幂等、权限 | 每条硬规则至少一正一反 |
| 属性测试 | 任何随机输入不破坏不变量 | 数值范围、库存守恒、时间单调 |
| 回放测试 | 同一快照与输入得到可解释结果 | 固定种子与版本 |
| 集成测试 | 原生调用、能力回执、存档恢复 | 每个 R2/R3 能力 |
| 叙事评估 | 事实、人格、因果和语气 | 正例、负例、对抗例 |
| 长程测试 | 数十到数百轮累积行为 | 关系、压力、记忆和事件 |
| 红队测试 | 越权、诱导、身份冒充、提示注入 | 每个安全边界 |

### 13.2 必测不变量

- 引擎数值是唯一生效来源。
- 任何资产的数量不会凭空增加或减少。
- 已完成任务不会被普通叙事重新打开。
- 死亡、永久关系和规则变更必须有明确来源。
- 同一个 request_id 重放不会重复执行。
- 过期快照的动作不会写入新状态。
- 保存、加载、迁移后核心事实不丢失。
- 模型失败时主循环仍可继续。

### 13.3 质量指标

建议同时记录：

- 结构通过率、重试率、回退率。
- 能力提案接受率、原生执行成功率、验证成功率。
- 重复执行率、冲突率、补偿率。
- 事实冲突率、人格 L-score、状态对齐 S/M-score、整体 PCC。
- 角色崩溃率、长程关系漂移、任务断链率。
- p50/p95 延迟、单轮 token、网络成本、每次回退原因。

单一“模型好不好”的分数不够。必须能够把失败拆成事实、规则、能力、执行、人格、叙事和基础设施七类。

### 13.4 基准场景与数据集

建立一套版本化的 golden scenarios，而不是只保存几段成功对话。每个场景至少包含初始快照 hash、玩家输入序列、可见信息、预期不变量、允许的结果集合、固定 seed、模型 profile 和失败分级。场景按以下五类组织：

| 类别 | 例子 | 主要指标 |
| --- | --- | --- |
| 状态完整性 | 交易、扣款、死亡、任务完成、存档迁移 | invariant violation、postcondition success、stale-write、duplicate execution |
| 世界与因果 | 延迟事件、因果链、规则覆盖、时间压缩 | fact precision/recall、temporal violation、causal edge precision、延迟后果校准 |
| 角色与社交 | 人格冲突、关系变化、信息不对称、协作 | PCC/L-score、关系漂移、memory precision、task continuity |
| 安全与恢复 | 注入、越权、供应商失败、并发冲突 | 拦截率、错误分级准确率、恢复成功率、审计完整率 |
| 玩家体验 | 可信度、自主感、惊喜、困惑、疲劳 | 人评量表、任务完成率、投诉率、回访率 |

每个指标必须写明分母、时间窗口、版本和最低门槛。BALROG、SOTOPIA 和 MACHIAVELLI 可以提供场景设计和指标启发，但不能替代目标游戏的专属 golden scenarios。

### 13.5 玩家研究与统计报告

涉及人格、社交、叙事涌现或玩家自主感的结论，至少做小规模人工评审，再决定是否扩大自动化。报告样本数、招募条件、任务顺序、模型版本、盲法、评分一致性、置信区间和失败例子；把“模型认为自然”与“玩家愿意继续玩”分开记录。Player-Driven Emergence 和 Collaborative Quest 的玩家研究可以作为实验设计参考，但它们的小样本文本或 Minecraft 结果不能直接外推到其他题材。

## 14. 运营、回放与版本

### 14.1 事件账本

每个动作至少保留 request、snapshot、proposal、validation、execution、receipt、projection 六类记录。日志里不要写密钥和不必要的玩家隐私；保留足以重放的规范化输入、版本和随机种子。

### 14.2 版本锁定

回放结果绑定 schema_version、rules_version、prompt_version、model_profile、adapter_version 和 seed。升级任何一个版本，都要重新跑基线样本，比较状态差异与叙事差异。

### 14.3 失败恢复

启动时扫描未闭合动作：读取原生状态；若已生效则补回执，若未生效则标记冲突或重新排队，不能无条件重放。扩展状态与原生状态不一致时，以原生读取结果为准，并留下修复记录。

### 14.4 性能与成本

低风险查询优先本地规则；只把必要字段送入模型；摘要、事实和记忆按角色与场景过滤；高风险动作才调用监督模型。网络请求要支持取消、重试上限和备用模型。不要为了追求“全世界每帧都由模型思考”而破坏游戏帧率。

## 15. 分阶段落地路线

### 阶段一：只读观察

接入原生事件监听、状态快照、实体目录和日志，不改变游戏。目标是证明能正确读取人物、物品、时间、任务、经济和存档。

### 阶段二：对话与叙事

加入上下文构建、结构化回复、人格一致性和本地回退。此阶段只做查询和叙事，不写核心状态。

### 阶段三：低风险扩展状态

加入记忆、关系候选、任务委托、世界事实和事件摘要。所有写入有修订号、幂等键和保存迁移。

### 阶段四：原生能力

逐项接入回访、交易、库存、战斗或其他原生能力。每项能力都要有前置条件、执行器、回执、验证和补偿。

### 阶段五：预测与长程模拟

加入延迟后果、多尺度时间、分支预测、事件调度、涌现监测和多智能体协调。

### 阶段六：质量闭环

加入回放集、人格评估、自动红队、跨模型评审、性能指标、版本基线和线上恢复。

### 15.7 接入符合性等级与退出门槛

用 G0-G5 记录系统实际达到的范围，避免把“能聊天”描述成“完成了世界模拟”：

| 等级 | 对应阶段 | 必须交付 | 退出门槛（项目起始值） |
| --- | --- | --- | --- |
| G0 | 只读观察 | 快照、实体目录、原生事件和日志 | 快照一致性不低于 99.9%，核心事实抽样可复核 |
| G1 | 对话与叙事 | schema、可见性、人格检查和本地回退 | schema 通过率、事实冲突率、回退率均有基线 |
| G2 | 扩展状态 | 记忆、关系、任务、事件、迁移 | 固定种子回放无核心不变量破坏，写入可追溯 |
| G3 | 原生能力 | 能力目录、适配器、回执、幂等和补偿 | 每项能力 postcondition 可验证，重复请求不重复执行 |
| G4 | 长程世界 | 延迟后果、时间压缩、多主体、预测校准 | N 轮回放无状态破坏，关系和任务断链率达到项目门槛 |
| G5 | 线上运营 | 监控、红队、SLO、成本和版本恢复 | p95 延迟、回退率、恢复时间和隐私审计均达标 |

每个门槛都要绑定构建号、数据集、指标脚本和责任人。研究论文最多帮助选择 G1-G4 的实验方法，不能替代 G3-G5 的产品验收。

## 16. 两个工程案例的抽象

### 16.1 E:\aigame2_publish 的可迁移模式

主工程把世界状态、规则、事件、记忆、RAG、模型调用和 UI 投影拆成独立模块。可迁移的重点包括：

- buildStateContext：把角色、近期事件、状态、背包、长期记忆、NPC、世界事实和因果图整理成模型上下文。
- buildAdvancePrompt：按场景和质量模式组装上下文，而不是把所有存档原样拼接。
- parseJSON 与 postParseSchemaCheck：先解析，再做 schema 检查，再由 sanitize 逻辑兜底。
- validateAIBoundary：集中检查线程连续性、物品、NPC、世界事实、叙事契约、属性变化、奖励和战斗。
- refreshWorldFacts 与 retrieveFacts：从当前状态刷新事实，再按查询返回有限相关内容。
- hierarchical-summarizer：按日、周、月生成摘要，控制长程上下文。
- event-scheduler：结合截止时间、关系、因果、最近互动和记忆压力，产生有限的事件重点。
- world-time：把时间推进、压缩、动作投影和叙事时间分开。

这些模块在题材上是修仙模拟，但接口职责适用于任何长程世界。证据类型为 E3/D1/X3：这是项目内观察和实现抽象，不是公开基准，也不自动证明跨引擎性能。

### 16.2 AIWorldPawnshop.dll 的可迁移模式

该 Mod 的运行时把“人物回复”和“世界监督”分开，形成一条可用于插件接入的最小闭环：

- WorldRuntime：加载配置、世界存档、模型提供方、本地回退和能力适配器。
- GameConversationContext：把原生人物档案、原生物品、关系、公开事实、已知人物和活动事件组成上下文。
- CharacterConsistencyGuard：在人物回复返回前检查自称、身份和原版角色别名。
- ConversationActionResolver：把自然语言中的回访、找货、交换和补付归一化为明确提案。
- CapabilityRegistry：用风险级别、权限、前置条件、安全时机和幂等字段描述能力。
- EchoWeaveRuntime 与 IntentLedger：记录快照、修订号、提案、执行、结果、冲突和恢复。
- GmModificationEngine：只允许白名单字段、有限幅度、有限期限和可验证执行器。
- Native*Adapter：把扩展提案接入原生来客队列、交易、库存和预算，并读取回执。
- LocalFallbackEngine：模型不可用时仍按本地规则生成可用回复。

可迁移的核心不是“当铺”业务，而是“上下文建模、能力目录、原生适配、账本、验证和回退”这六个边界。证据类型为 E3/D1/X3；迁移到新游戏时，必须重新验证原生写入点、存档兼容、权限和性能。

### 16.3 案例证据边界

| 来源 | 可迁移假设 | 不可直接迁移的细节 | 验证计划 |
| --- | --- | --- | --- |
| E:\aigame2_publish | 状态上下文、事实检索、事件调度和分层摘要可以拆成独立模块 | 具体题材字段、提示模板、RAG 数据和时间尺度 | 用目标游戏快照做字段覆盖、权限和长程回放 |
| AIWorldPawnshop.dll | 能力目录、原生适配器、账本、回执和本地回退形成最小闭环 | DLL 类型名、当铺业务、特定调用顺序和数值 | 对每个新能力做前置条件、postcondition、幂等和恢复测试 |

两个案例都属于项目内证据，不能替代公开研究或目标游戏的独立验收。

## 17. 反模式与替代方案

| 反模式 | 直接后果 | 替代方案 |
| --- | --- | --- |
| 让模型直接改 JSON 存档 | 数值越界、无法回放 | 提案 + 规则引擎 + 迁移 |
| 把全部存档塞入提示词 | 泄漏、超长、权威混乱 | 可见性过滤 + 摘要 + 检索 |
| 只有聊天没有回执 | 玩家听到已发生但游戏没发生 | 能力执行器 + postconditions |
| 用一张人设卡维持百轮角色 | 情绪僵硬或人格漂移 | L/M/S 状态与评估闭环 |
| 用生成文字修复事实冲突 | 时间线被悄悄改写 | 标记待解释，状态不回滚 |
| 每次失败都重试同一提示词 | 延迟和费用上升 | 分级回退和错误分类 |
| 没有幂等键 | 重复扣款、重复任务 | 规范化参数 + 账本状态机 |
| 只测单轮样例 | 长程断链和关系漂移 | 固定种子回放 + 长程压力测试 |
| 只看模型分数 | 找不到工程瓶颈 | 结构、事实、能力、执行、叙事分维度 |

## 21. 研究证据附录

### 21.1 阅读规则

本附录把公开研究转成可追踪的工程证据。论文中的数字、阈值、样本数和性能结果只对原论文任务、模型、版本和环境成立；迁移到目标游戏前必须重新测量。没有任何一篇公开研究同时证明“原生引擎裁判、能力目录、审计回放、动态角色和长期世界模拟”这套完整闭环。完整闭环是多条证据与项目内工程经验拼接出的方案，最终成立与否由目标游戏的回归、权限、故障和玩家测试决定。

证据标签沿用第 0.2 节：E0 是工程不变量，E1 是基准或多项研究，E2 是单项研究、公开原型或架构框架，E3 是项目内观察，H 是启发式；D1、D2、D3 分别表示原生状态、相邻工具环境和理论/类比的直接性；X1、X2、X3 分别表示跨题材复现、有限迁移和未验证的外部效度。

### 21.2 角色、记忆与认知架构

| 研究 | 核心观察 | 可迁移原则 | 边界与标签 |
| --- | --- | --- | --- |
| [Generative Agents](https://arxiv.org/abs/2304.03442)（2023） | 记忆流、反思、检索和计划在 25 人沙盒中产生可信的个体与社会行为，消融显示观察、计划和反思均有贡献 | 事件原文、分层记忆、反思摘要、情境检索和计划可以分层实现 | 小规模文本沙盒、定性评价，未证明大规模实时一致性；E2/D2/X2 |
| [Cognitive Architectures for Language Agents](https://arxiv.org/abs/2309.02427)（2023） | 用模块化记忆、结构化行动空间和决策过程整理语言代理 | 以模块职责组织上下文、能力和记忆，而不是依赖一个长提示词 | 架构综述，不是统一实现或性能保证；E2/D3/X2 |
| [MemoryBank](https://arxiv.org/abs/2305.10250)（2023） | 通过相关记忆召回、持续更新以及基于时间和重要性的强化/衰减支持长期互动 | 记忆要有重要度、时间、权限、来源和遗忘策略 | 聊天与模拟对话案例，遗忘曲线是启发式；E2/D2/X2 |
| [Character-LLM](https://arxiv.org/abs/2310.10158)（2023） | 将人物档案、经历和情绪状态用于角色扮演与角色记忆评估 | 把身份、经历、情绪和表达风格分开建模 | 访谈评测较窄，未证明长期多主体稳定；E2/D2/X3 |
| [LLM Agents in Interaction](https://arxiv.org/abs/2402.02896)（2024） | 角色提示的语言代理在交互后表现出不同程度的人格一致性和语言对齐 | 需要用跨轮轨迹评估人格稳定与适应，而不是只看单句 | 文本协作任务，不能直接证明游戏行为一致性，也不证明 PCC/PCR/PDS 阈值；E2/D2/X3 |
| [Large Language Models and Games: A Survey and Roadmap](https://arxiv.org/abs/2402.18659)（2024） | 归纳 LLM 在游戏中作为玩家、NPC、助手、评论者、分析者、GM、机制和设计工具的角色 | 先声明模型责任边界，再决定上下文、能力和评测范围 | 综述不是性能证明；E2/D3/X2 |

### 21.3 动作、工具与跨环境接入

| 研究 | 核心观察 | 可迁移原则 | 边界与标签 |
| --- | --- | --- | --- |
| [SayCan](https://arxiv.org/abs/2204.01691)（2022） | 高层语言计划必须通过已有技能和价值/可供性判断才能落到可执行动作 | 能力目录、前置条件和环境可执行性先于自然语言承诺 | 机器人技能与价值函数，迁移到游戏需重建适配器和校验器；E2/D2/X2 |
| [ReAct](https://arxiv.org/abs/2210.03629)（2022） | 将推理与工具动作交错，利用环境反馈修正计划并减少错误传播 | 使用观察—提议—执行—回执循环，保留外部结果 | 依赖提示和工具设计，推理轨迹不等于忠实解释；E2/D2/X2 |
| [Voyager](https://arxiv.org/abs/2305.16291)（2023） | 自动课程、可执行技能库、环境错误和自我验证支持 Minecraft 长期探索与跨世界复用 | 记录可执行技能、失败原因和验证结果，支持组合与复用 | GPT-4 与 Minecraft API 场景，未覆盖社会关系和原生审计存档；E2/D2/X2 |
| [Scaling Instructable Agents Across Many Simulated Worlds（SIMA）](https://arxiv.org/abs/2404.10179)（2024） | 以图像和自然语言为输入、键鼠为输出，报告了跨多个 3D 和商业游戏的初步执行结果 | 没有 API 时可用视觉控制做原型或回退，但必须加状态对账 | 看不到隐藏状态和规则，不能保证确定性写入与回放；E2/D2/X2 |
| [Cradle](https://arxiv.org/abs/2403.03186)（2024） | 以截图和键鼠构成统一电脑控制接口，在商业游戏中执行长任务 | 可作为无 API 接入的探索路径或人工接管辅助 | 感知动作脆弱且缺少内部事实接口，不宜替代原生适配器；E2/D2/X2 |

### 21.4 长程学习、社交、叙事与安全

| 研究 | 核心观察 | 可迁移原则 | 边界与标签 |
| --- | --- | --- | --- |
| [Reflexion](https://arxiv.org/abs/2303.11366)（2023） | 将外部或内部反馈转成语言复盘并写入情节记忆，可跨试次改善决策 | 复盘只更新提议策略和记忆，不更新核心事实 | 错误复盘可能累积，不能替代规则回执；E2/D2/X2 |
| [SOTOPIA: Interactive Evaluation for Social Intelligence in Language Agents](https://arxiv.org/abs/2310.11667)（2023） | 用开放社交场景和统一评测观察协作、竞争、交换和策略沟通 | 为 NPC 社会目标、关系和沟通设计独立评测集 | 文本角色扮演，社会得分不等于世界状态正确；E1/D2/X2 |
| [Do the Rewards Justify the Means? Measuring Trade-Offs Between Rewards and Ethical Behavior in the MACHIAVELLI Benchmark](https://arxiv.org/abs/2304.03279)（2023） | 在 134 个选择冒险游戏和 50 万以上场景中量化权力寻求、欺骗、伤害和伦理违规与奖励的张力 | 将安全和伦理行为纳入场景、指标和审计，而不是只看任务完成率 | 文本游戏、LM 标注和代理指标，不能等同现实危害评估；E1/D2/X2 |
| [BALROG: Benchmarking Agentic LLM and VLM Reasoning On Games](https://arxiv.org/abs/2411.13543)（2024） | 跨游戏基准显示模型在简单任务上部分成功，但复杂长程和视觉决策明显薄弱；部分模型加入视觉输入后反而变差 | 用多难度游戏和细粒度指标做能力回归，单独报告视觉输入影响 | 基准结果不等于目标产品体验；E1/D2/X2 |
| [Player-Driven Emergence in LLM-Driven Game Narrative](https://arxiv.org/abs/2404.17027)（2024） | 28 名玩家与 GPT-4 NPC 互动后出现原叙事未预置的节点，可从日志构建叙事图 | 记录玩家路径和新节点，评估发现、探索和惊喜体验 | 小样本文本冒险，涌现检测是后验分析且难复现；E2/D2/X3 |
| [Collaborative Quest Completion with LLM-driven Non-Player Characters in Minecraft](https://arxiv.org/abs/2407.03460)（2024） | 28 名玩家与两个 GPT-4 NPC 在 Minecraft 任务中形成可分析的协作模式 | 测试玩家与 NPC 的分工、误解、补救和任务连续性 | 单一小游戏和小样本，语言模型缺少丰富状态/视觉理解；E2/D2/X3 |
| [Emergent social NPC interactions in the Social NPCs Skyrim mod and beyond](https://arxiv.org/abs/2207.13398)（2022） | CiF-CK 社会架构以 Mod 形式组织开放世界 NPC 社交行为 | 规则化社会架构与 Mod 接入可以先于模型生成建立 | 非模型方法且针对特定游戏，不能当通用性能证据；E2/D1/X3 |

### 21.7 可复现实验与验收协议

最低复现包如下：

~~~
build_id
adapter_version
schema_version / rules_version
prompt_version / model_profile
seed / random_stream
initial_snapshot_hash
input_sequence
visible_context_hashes
proposals_and_validation_traces
native_receipts
projection_outputs
metric_script_version
failure_samples
~~~

推荐执行顺序：先冻结版本和初始快照，再用固定输入序列运行在线接入；保存完整 trace；在同一版本离线重放；比较状态不变量、回执、因果边和投影差异；最后在替换模型、规则、适配器和网络条件后重复运行，分别归因。任何成功率都要同时报告拒绝、延期、冲突、回退、重复执行和状态修复的分母。

### 21.8 研究空白与验证计划

| 优先级 | 已知 | 未知 | 验证计划 |
| --- | --- | --- | --- |
| 高 | 研究多集中于短任务、小规模角色或单一环境 | 数百/数千轮后的因果一致性、记忆污染和关系漂移 | 固定种子长程回放、故障注入、记忆精度和任务断链统计 |
| 高 | 能力接地和视觉控制已有原型 | 跨引擎、跨 Mod、跨存档格式的迁移成本 | 建立至少两种引擎/接口的同一能力契约，比较适配器工作量和失败率 |
| 高 | 研究环境通常暴露较少隐藏状态 | 部分可观测、隐性规则和玩家私密信息如何安全接入 | 信息隔离红队、可见性证明、跨角色泄漏回放 |
| 中 | 社交基准能区分模型能力 | 多主体公平、资源争用、极化和优先级饥饿 | 并发压力测试、角色群体指标和人工审查 |
| 中 | 反思和记忆可改善局部任务 | 供应商、模型和提示变化造成的漂移 | 版本锁定、黄金样本、差异回放和回退演练 |
| 中 | 研究报告了能力或体验指标 | 延迟、成本、质量和玩家自主感的最优点 | p50/p95/p99、token/cost、玩家研究和分层实验 |
| 低 | 生成式视觉环境能提高表现或演示效果 | 视觉生成结果的版权、可控性和长期资产一致性 | 资产来源审计、内容审核、长轨迹一致性测试 |

链接和版本以 2026-10-18 的公开页面为准。论文结论、公开原型和项目内观察都必须在目标游戏中重新验证，不能直接当作生产保证。
